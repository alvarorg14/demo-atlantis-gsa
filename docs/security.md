# Security model

The Atlantis VM runtime identities are separate from the per-environment Terraform execution identities. Each backend and Google provider explicitly impersonates the relevant execution identity, and each root supplies a single fixed project ID to the module. GCP IAM and bucket permissions are the actual authorization boundary; the configuration and naming validation can be modified by a PR author. Subject to effective GCP IAM, each execution identity can create service accounts in its own project and access its own state bucket. No roles or bindings are managed here.

The NoPRO runtime can impersonate both DEV and PRE, so those environments share a runtime trust boundary even though their projects, identities, roots and state are separate. A malicious change executed by that runtime may use either identity. PRO has a separate Atlantis runtime and must remain isolated by GCP IAM, bucket permissions, server configuration and GitHub controls. Installing the repository or cloning it provides no GCP credentials or impersonation rights. Developers should not automatically receive production impersonation, direct GSA creation, state access or VM credentials.

State can contain service-account metadata, identifiers and resource mappings. It is not a secret store and should nevertheless be treated as sensitive. State is stored and locked remotely in separate pre-existing GCS buckets; never commit state, plans, access tokens or credentials. The module creates no keys. Granting workload permissions to an account is a separate privileged, reviewed process; service-account creation alone does not grant the new identity access to resources.

`prevent_destroy` is a guard against accidental deletion only while the resource declaration remains. Removing that declaration removes the lifecycle rule; IAM currently lacks delete permissions. The create-focused identity also lacks general update permissions, so metadata changes can fail. Naming validation and a static scanner are not security boundaries, and code review and GCP IAM remain essential. No OPA enforcement currently exists. A future platform-controlled server-side OPA/Conftest policy, stored outside this repository, should allow only approved GSA creation, validate names and target projects, deny deletes/replacements, IAM grants and keys, and reject unexpected provider configurations where detectable. Such policy needs a separate change to the setup; local Rego files here would not enforce it.
